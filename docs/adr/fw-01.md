# FW-01 — Keep deterministic functions and a closed runtime dependency set

- Status: amended; covers FW-01 through FW-04.
- Original record: 2026-07-24, `dc2877c` (`ARC-008`).
- ADR backfill: 2026-10-17.
- Authority: [architecture §8](../architecture.md#8-framework-boundary)
  remains normative. Maintain rationale and amendments under
  [the ADR policy](README.md).

## Context

Publication, prune, repair, and recovery look like workflows, but version 1
has a fixed, linear, single-writer sequence whose branches describe failure
handling. The filesystem already supplies the durable authority, and the
architecture's crash matrices specify the permitted intermediate states.

## Decision

Implement version 1 with ordinary deterministic Python functions and typed,
append-only checkpoint records. Do not introduce a workflow engine,
state-machine library, task queue, DAG framework, actor system, or agent
framework (FW-01). Journals record durable filesystem facts for recovery;
normal execution does not read them to select its next orchestration step
(FW-02).

Keep runtime dependencies to `huggingface-hub`, `pydantic`, `typer`, the
resolved Hub client's required transfer backend, and the standard library
(FW-03). A new dependency requires a recorded material correctness benefit
that the standard library cannot supply; convenience, familiarity, or fewer
lines are insufficient (FW-04).

Revisit the framework choice only if requirements introduce branching
workflow graphs, human approval states, or durable distributed
orchestration. In that case the recorded future choice is Pydantic AI,
with a deliberate contract and decision change before implementation.

## Rationale and alternatives

A workflow engine would add a second state authority and persistent store
beside the filesystem, undermining [AD-12](ad-12.md). It would spread a
readable crash matrix across the engine's persistence model and hfcache's
own recovery model without addressing an unmet version-1 requirement.

The original record rejects adding a general framework early, choosing a
different framework when the stated trigger arrives, or gradually growing
a home-built engine inside hfcache. It does not claim Pydantic AI is needed
or permitted as a present runtime dependency.

## Consequences

Domain functions, durable schemas, and filesystem boundaries stay directly
inspectable. Adding background download overlap in AD-19 does not add an
orchestration framework or a new durable queue. Build-time Cockpit
dependencies have their separate recorded boundary; they do not broaden the
Python runtime set.

## 2026-10-17 amendment (API-001)

[Decision 108](decision-108.md) authorizes the explicit transport dependency
additions incrementally; [decision 109](decision-109.md) permits only a bounded,

## 2026-10-17 implementation amendment (API-005)

[Decision 112](decision-112.md) adds the actual direct base HTTPX dependency and
optional FastAPI/Uvicorn server extra, including their required transitives,
with Python 3.14 lock/install evidence. Maintained verified transports, HTTP
parsing, security dependencies and ASGI lifecycle justify this scoped FW-04
addition. The standard library retains TOML, serialization, hashing, files,
locking and logging. No workflow framework, MCP dependency, server listener or
production installation is added; the remaining exclusions above stand.

## 2026-10-17 receipt implementation amendment (API-007)

[Decision 114](decision-114.md) implements the service-private non-resuming
registry permitted by decision 109. Independently versioned JSON receipts are
the authoritative admission/key binding; their indexes are derived. Receipts
never reconstruct commands from archive journals, automatically restart work or
select domain checkpoints. Finite storage refuses admission rather than erasing
unexpired or uncertain history. This scoped FW-01 exception adds no database,
broker, workflow abstraction, archive format or runtime dependency. The heavy
execution lane and verifier remain later tasks; FW-02's normal-execution rule
is unchanged.
