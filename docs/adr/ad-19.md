# AD-19 — Overlap downloads with hashing through one bounded producer

- Status: accepted; context propagation amended by [decision 111](decision-111.md)
  and daemon drain ownership clarified by [decision 115](decision-115.md).
- ADR backfill: 2026-10-17; original decision and implementation dates are
  recorded below.
- Authority: the cited architecture contract remains normative. This ADR
  records rationale and history; maintain it under [the ADR policy](README.md).

## Context

SHA-256 reads of large NFS snapshots can occupy the storage path for many
hours while WAN bandwidth remains idle. Concurrent repository transfers,
however, could multiply Xet's internal resource usage and exceed the writer
service's memory and capacity model.

## Decision

For continuation-enabled syncs, resolve and estimate the selected queue
and admit its aggregate capacity before transferring. Run one background
repository-download producer while the main thread hashes and publishes
completed snapshots in configuration order. Give the one active transfer
the existing `sync.max_workers` budget. Strict stop-on-error remains serial.

## Rationale and alternatives

One producer overlaps independent WAN and local-read work without adding
another archive writer or multiplying transfer concurrency. Queue-wide
admission prevents knowingly starting work beyond the configured reserve.

Decision 94 rejects multiple concurrent repository downloads because they
multiply Xet concurrency; a separate sync process because it contends for
the lock or mutates cache outside ownership; and `HF_XET_HIGH_PERFORMANCE`
because its installed-version resource model exceeds the memory bound.

## Consequences

Ordinary publication journals may wait at `download_completed`; no queue
format is introduced. Results, generation assignment, publication, and
errors remain deterministic. Cache writes/scans are serialized and
retention waits until all queued snapshots are consumed. Copy staging
rechecks capacity and holds the allocation guard. Foreground failure
cancels unstarted work and joins the sole active transfer before releasing
the archive lock, without downloading the untouched queue remainder.

**API-004 amendment (2026-10-17, [decision 111](decision-111.md)).**
The producer receives a separate copy of its active execution context through
`submit_with_context`; emitted events retain run/request/operation correlation.
Return or failure restores the worker's earlier scope. This changes no producer
count, cache guard, lock, ordering, memory or capacity policy.

**API-008 amendment (2026-10-17, [decision 115](decision-115.md)).**
The heavyweight runner closes admission before drain and joins accepted domain
work, which must still join its active sync producer before releasing the common
archive flock. Losing or stopping an API client is not cancellation of that
writer. Recovery proof must identify the actual operation/executor, preserving
the original producer count, cache, capacity and ordering rules.
