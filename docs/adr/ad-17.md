# AD-17 — Use one writer host and one local exclusive lock

- Status: accepted; amended by decisions 110/115 (2026-10-17) and
  [120](decision-120.md)/[121](decision-121.md) (2026-10-18).

## Context

The deployment grants archive write access to one dedicated host.
Concurrent local commands still need mutual exclusion, but a distributed
lock would add failure modes without providing an additional authority
boundary.

## Decision

Enforce one writable host through the exact-host server export policy.
Serialize archive-affecting commands through the same local exclusive lock
under `/run/hfcache`, outside NFS. Do not add leader election or
distributed coordination. A second writer is an architectural change.

## Rationale and alternatives

A local lock is sufficient when the server permits only one host to
write. Avoiding NFS locks removes unnecessary distributed locking behavior
from the archive's correctness assumptions.

The original record rejects distributed locking and lock files on NFS,
which buy nothing under the single-writer deployment. Per-command locks
would not exclude different mutating commands from one another.

## Consequences

Sync, verification, prune, purge, repair, recovery, and explicit quarantine
cleanup honor the shared archive lock where their contracts require it.
The download-ahead worker remains inside the owning sync process and must
finish before that lock is released. The export's host restriction and
local lock solve different parts of the single-writer guarantee.

## guarded command services amendment (2026-10-17)

[Decision 110](decision-110.md) tightens the common-lock boundary: every
non-estimate verification proves storage safety and retains ownership through
scope resolution, hashing, report persistence and complete catalog merge.
Probing doctor and explicitly confirmed initialization also own the common
lock, while using their own checks so uninitialized storage remains diagnosable
and initializable. Read-only doctor and initialization inspection take no lock.
Public command services acquire once; adapters/runners must not pre-lock them.
This amendment changes no durable schema or systemd scheduling authority.

## bounded runner and private verifier execution amendment (2026-10-17)

[Decision 115](decision-115.md) adds one bounded in-process lane without replacing
the cross-process archive flock. One absolute deadline covers queue residence
and the remaining lock wait. The service retains sole lock acquisition and runs
a fresh admitted-policy comparison inside ownership before mutation; the runner
does not pre-lock the service. The separate verifier owns its own complete
verification lock/persistence boundary. Metadata/store/daemon locks grant no
archive mutation authority. No distributed lock or second writer is introduced.

## maintenance routes maintenance transport amendment (2026-10-17)

[Decision 117](decision-117.md) exposes the existing maintenance services through
separate typed preview/apply URLs. Apply retains service-owned common flock,
fresh admitted-policy comparison and domain scope/guard/evidence revalidation;
previews grant no later authority. Initialization additionally requires its
restart-only maintenance gate and explicit configured root/UUID confirmation,
using its own locked initialization checks. No adapter pre-locks a service or
extends daemon/store locking into archive mutation authority.

## CLI operation observation observer ownership clarification (2026-10-18)

[Decision 120](decision-120.md) moves operational CLI modes to typed HTTP without
a local mutation backend. The server/service or private verifier retains flock,
preflight, recovery and persistence ownership. Stopping a CLI/client unit or
timing out its observer never proves that executor stopped or its lock released.
Server drain and exact verifier reconciliation remain the authority; mandatory
key/operation handles permit observation without duplicate execution.

## scheduled observation unit lifecycle amendment (2026-10-18)

[Decision 121](decision-121.md) preserves shared local runtime lock inodes across
client/server/worker unit stops. Socket activation gives one application all its
enabled listeners, not separate registries. Scheduled clients retain private
observer ownership and pending handles but gain no archive-lock authority.
Stop admission/activation and drain the actual server/private executor before
release/mount work; a stopped oneshot or free flock alone proves no outcome.
Repository fixture rehearsals do not prove installed cgroup/SELinux/NFS behavior.
